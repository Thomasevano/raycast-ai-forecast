# Public reset-source research

Assessed 2026-11-12. An exceptional reset is a discretionary provider-wide or plan-scoped intervention, not the normal replenishment of one account's allowance. A banked reset is a grant that must be redeemed; it is not evidence of an immediate refill. Incident reports, usage credits, API rate limits and normal scheduled resets are not exceptional-reset probabilities. Public signals must not change local allowance forecasts or alerts.

The extension fetches only the two Codex sources described in the [README](../README.md#optional-community-reset-signals). The links below are research references, not additional integrations. Local quota forecasts still support Claude and Codex only.

## Claude and Claude Code

**Candidates exist, but do not integrate a Claude exceptional-reset probability yet.** The issue is data semantics and reliability, not the absence of an API.

- [WhenReset's public Claude forecast](https://whenreset.app/api/forecast?product=claude) returned unauthenticated JSON with `updated_at`, `data_as_of`, sample size and 24-hour, 48-hour and seven-day fractions. It labels its target “global hard reset (banked excluded)”; its [API documentation](https://whenreset.app/api/) says the model is the fraction of observed historical gaps within each horizon, without conditioning on time already elapsed, and describes five-minute caching. This is a historical frequency estimate, not an Anthropic schedule or a calibrated personal probability. The interface is documented, but the forecast endpoint is not under the documented `/api/v1/` versioning policy. The docs request attribution of the upstream archives when displaying their data; no account data or credentials are required for the public request, although the host necessarily receives the requesting IP address.
- [Claude Reset's documented API](https://claudereset.org/developers/) republishes that same model, not an independent estimate; its [live JSON](https://claudereset.org/api/v1/forecast.json) includes build, event-check and signal-fetch timestamps and advertises a versioned, no-key interface with five-minute caching. Attribution is appreciated. **Classification is a material problem:** its own documented timeline labels the November 10 announcement `regular` and `global`, while the quoted announcement says the reset can be used later. [Anthropic's own description](https://support.claude.com/en/articles/17007452-what-is-a-limit-reset) confirms such grants are redeemed by the account holder. The site's [method page](https://claudereset.org/forecast-method/) says the shared Claude sample is too small for its own Claude backtest. Its homepage also simultaneously displayed an estimate and an unavailable warning during this assessment. Do not treat the displayed forecast as a verified hard-reset-only probability. The original [announcement link](https://x.com/ClaudeDevs/status/2120275296637321476) could not be read directly without credentials; the classification discrepancy is based on the site's own quoted text and official grant documentation.
- [AI Resets](https://airesets.dev/forecast) publishes an experimental Claude full-reset waiting-time model, explicitly warning that its backtest has no advantage over a flat baseline. Its unauthenticated [forecast JSON](https://airesets.dev/forecast.json) exposes `asOf`, `p24`, `p48`, `p72` and build-snapshot freshness; the payload states CC BY 4.0 and requests attribution and a method-page link. Its Claude forecast identifies September 22 as the last full reset, whereas [Anthropic's September 22 announcement](https://www.anthropic.com/claude-opus-5-5) describes a reset users can save and redeem. This apparent grant/full-reset mismatch and the weak backtest preclude a recommendation. The forecast page's linked source repository was unavailable when checked, so an independent ledger audit was not possible.
- [Reset Radar's loader](https://limitreset.dev/js/api.js) fetches public [data JSON](https://limitreset.dev/data/data.json); its Claude `global_reset` entry supplies a 24-hour target and generation timestamp, distinct from `normal_recovery`. The observed entry marked calibration experimental and reported no historical events; the file was already older than its advertised 30-minute maximum age despite its `fresh` flag. Its [method page](https://limitreset.dev/about.html) describes a heuristic, not a validated calibration. No public versioning, reuse license or stable API commitment was verified for this site-internal JSON; do not integrate it as a probability.
- [LimitReset's documented API](https://limitreset.net/api-docs) is public and no-key, but the observed [Claude response](https://limitreset.net/api/v1/claude/latest) says `basis: insufficient-data` and no latest event. Its zero-valued fields are not evidence of zero chance. Documentation describes forecast as null, so consumers should not assume a stable forecast contract.

**Official alternatives, not predictions:** [Anthropic's usage guidance](https://support.claude.com/en/articles/11647753-how-do-usage-and-length-limits-work) says Claude and Claude Code share usage limits. Paid plans generally have a five-hour session window starting with the first message and account-specific weekly resets; verified Ultra accounts are an exception to the five-hour limit. The account's Settings → Usage shows actual timing. A separately granted reset may need redemption in Claude's settings, and does not change the usual weekly schedule or refund paid credits ([reset guidance](https://support.claude.com/en/articles/17007452-what-is-a-limit-reset)). The public, unauthenticated [Claude status summary JSON](https://status.claude.com/api/v2/summary.json) has component and incident timestamps, including a Claude Code component; it measures service health, not quota reset likelihood or account status.

## Gemini and Gemini CLI

**No verified exceptional-reset forecast for Gemini Apps or Gemini CLI was found in the assessed sources.** [AI Resets](https://airesets.dev/forecast) explicitly reports too little Gemini reset history to forecast. [LimitReset's Gemini API response](https://limitreset.net/api/v1/gemini/latest) returned no event and `insufficient-data`; its zero fields are not a forecast. No in-app forecast integration is justified on this evidence.

A related but different product, [AGY Resets](https://www.agyresets.com/), tracks public Gemini quota-reset announcements **in Antigravity**, and displays a time-bounded launch-based watch that it explicitly calls a heuristic, not a forecast. Its public [RSS feed](https://www.agyresets.com/feed.xml) contains dated past announcement items and links to source posts, not the watch's machine-readable prediction. The page was publicly accessible without credentials; a documented stable machine-readable forecast interface, reuse license and refresh guarantee were not verified. It cannot establish a forecast for Gemini Apps or Gemini CLI. The linked X announcements could not be independently read without credentials.

**Official alternatives, not predictions:** [Gemini Apps guidance](https://support.google.com/gemini/answer/16275805?hl=en) describes personal-app compute limits that refresh every five hours until the weekly limit; this is not a global intervention. [Gemini API rate-limit documentation](https://ai.google.dev/gemini-api/docs/rate-limits) says per-project requests-per-day quotas reset at midnight Pacific time. That rule is for the Gemini API and must not be generalized to a Gemini Apps or Google-login CLI subscription. The [Gemini CLI quota documentation](https://github.com/google-gemini/gemini-cli/blob/main/docs/resources/quota-and-pricing.md) describes different authentication paths and `/stats model` for a snapshot of session usage and applicable limits; it still lists consumer Google-login tiers, but Google's newer [deprecation notice](https://developers.google.com/gemini-code-assist/docs/deprecations/code-assist-individuals) says those consumer CLI tiers stopped serving requests on June 18, 2026, and directs users to Antigravity. Standard and Enterprise have a separate deprecation schedule. These account views require the user's own authentication; they are not public anonymous reset feeds. The unauthenticated [Google Cloud incidents JSON](https://status.cloud.google.com/incidents.json) provides incident creation and modification times for Cloud services, not a comprehensive Gemini Apps status or a quota-reset forecast.

## DeepSeek

**No integration recommended:** no verified, currently issuing machine-readable forecast of exceptional broad DeepSeek quota resets was found in the assessed sources. [ResetBell's DeepSeek forecast-readiness page](https://resetbell.dev/en/stats?provider=deepseek&section=forecast) is a directly relevant public candidate: it explicitly excludes personal recovery, grants and plans, but at inspection reported zero eligible events, zero comparable samples, zero complete windows, and no eligible forecast. Its 30 days were unverified; the site explicitly says no record does not prove no reset occurred. A missing or unavailable estimate is not a zero probability.

[DeepSeek API limits](https://api-docs.deepseek.com/quick_start/rate_limit/) specify account-level concurrent requests, with HTTP 429 on excess; [pricing](https://api-docs.deepseek.com/quick_start/pricing/) describes per-token charges deducted from granted or topped-up balances. Neither is evidence of an exceptional, broad chat-product quota reset. These sources describe the API and do not establish all DeepSeek chat-app limits.

## OpenCode Go

**No integration recommended:** no verified public exceptional-reset forecast for Go was found in the assessed official documentation or searches for community Go/global-reset trackers. [Go's official documentation](https://opencode.ai/docs/console/go/) describes an optional subscription provider, not the open-source OpenCode harness itself; it lists 5-hour, weekly and monthly usage limits based on monthly-dollar allowances. Its [Activity announcement](https://opencode.ai/console/changelog/activity) describes account/workspace usage, renewal forecasts and each limit's reset time, not an extraordinary reset affecting many subscribers.

Do not conflate Go with OpenCode Zen/Console pay-as-you-go: [Console models documentation](https://opencode.ai/docs/console/models/) describes per-request, credit-funded usage and separately links Go's subscription. Using a DeepSeek or Grok model through Go is also not the same product or allowance as using that model directly.

[OpenUsage](https://openusage.sh/docs/providers/opencode/) describes personal Go quota meters and pacing projections requiring a console session; [opencode-go-quota](https://github.com/xingkaijun/opencode-go-quota) describes an API-key-based personal usage poll and extrapolation. Their differing access descriptions are not independently reconciled here; neither is a public exceptional-reset forecast. Do not introduce authenticated account reads or cookie collection for this feature.

## Grok, SuperGrok and Grok Bot

**Relevant machine-readable candidate, but do not integrate its forecast as a Grok/SuperGrok indicator now.** Independent [WhenReset Grok](https://whenreset.dev/grok) records extra announced events, distinguishes normal account resets, and explicitly says Grok Bot's allowance is separate from Grok chat/Imagine/Build. Its unauthenticated [JSON API](https://whenreset.dev/api/resets) returned `dataSchemaVersion: public-api-1`, `generatedAt`, `checkedAt`, `expiresAt`, source-check timestamps, `stats.grok.estimatedNextAt`, `estimate.asOf`, `estimate.method: bounded-wait-v2`, `estimate.target: reset-or-card-record`, and timestamped `events` with type, scope and source URLs. The estimate is a bounded historical timing reference mixing resets and cards, not a calibrated probability, an official schedule or a personal weekly reset. Events combine Grok and Bot; scope `all` alone does not establish which product the event affects. The site itself says the Grok 4.6 event handed out a redeemable reset token, while the corresponding table labels it a usage reset: classification needs independent verification before use. The original X posts were inaccessible without authentication; no claim of independent confirmation is made.

On the observed API response, `generatedAt` was 2026-11-12 22:27 UTC, `checkedAt` 22:25 and `expiresAt` 22:55. Those are response freshness metadata, not proof the underlying event coverage is complete. A second request returned HTTP 429; published rate limits and a stability guarantee were not established. The endpoint responded without credentials, but its [privacy policy](https://whenreset.dev/privacy) says hosting/security services process technical request data including IP addresses. No applicable redistribution license or terms were verified in the assessed pages. Avoid sending account usage or credentials, do not present estimates as certainty, and reassess source scope, licensing and interface reliability before considering a separately labelled community historical indicator.

Another public candidate, [AI Reset Tracker's Grok prediction page](https://ai-reset-tracker.netlify.app/grok-reset-prediction/), describes a seven-day community vote, not an official or calibrated probability. Its [public community JSON](https://ai-reset-tracker.netlify.app/api/community?provider=grok) returned without authentication and contained `startedAt`, `totalPredictions` and dated counts/percentages; the observed seven displayed dates each had zero votes despite `totalPredictions: 3`. No response-generated timestamp, explanation of that discrepancy, published stable API contract, or relevant licensing was verified. Its [static page](https://ai-reset-tracker.netlify.app/grok-reset-prediction/) showed an October 2–8 window despite being read November 12; it says live content requires the interactive tracker. Neither stale static dates nor zero-count vote percentages justify a forecast. Its privacy page provided no substantive data-handling details in the text retrieved; no quota data or credentials were submitted.

[Official Grok FAQ](https://docs.x.ai/grok/faq) describes paid users' shared weekly pool and the individual reset time in Settings → Usage; separately purchased Extra Usage Credits are consumed after the allowance. [xAI API documentation](https://docs.x.ai/developers/rate-limits) specifies team/model RPS and TPM limits, and [API billing](https://docs.x.ai/console/billing) describes prepaid credits or invoicing. These are not interchangeable with exceptional broad consumer or Bot resets. [Grok overview](https://docs.x.ai/grok/overview) describes the consumer product, while [WhenReset](https://whenreset.dev/grok) explicitly distinguishes Bot.

## Search boundary

Searches included `Claude Code global quota reset forecast probability public tracker API site`, `Gemini CLI global quota reset prediction forecast probability public API`, `"limitreset.dev" "api" prediction claude forecast`, and `"gemini" "global reset" forecast quota probability tracker`, plus official Claude usage-limit and Gemini CLI quota searches. Candidates and official documentation were read directly rather than relying on snippets; [WhenReset Today](https://whenreset.today/claude-code/) was also checked as an announcement/history tracker. Search results are time-sensitive and not exhaustive. No provider credentials, account APIs or personal quota data were used. A public GET still discloses network metadata to the contacted host; a future integration would need explicit privacy, freshness, availability, attribution and licensing review.
